# 日本ゲーム観測台 / Japan Game Observatory

日本游戏厂商新作发布的每日监测台。定期扫描日本游戏媒体，按
**公司 → 作品 → 新闻原文 → 参考 URL → 实机/预告视频 → 全球玩家舆论期待度**
六个维度编排成可视化页面。

## 观测窗口

窗口为**滚动最近 2 个月**，即 `<今日 − 2 个月> ~ <今日>`。

| | |
|---|---|
| 当前窗口 | **2026-07-15 ~ 2026-09-15** |
| 明天自动变为 | 2026-07-16 ~ 2026-09-16 |
| 记录字段 | `meta.window`，格式 `<起> ~ <止>（滚动最近 2 个月）` |

**收录判断同样按这个窗口**：只收发表日 / 发售日 / 重要进展落在窗口内的作品；
窗口外的旧作不新建条目，但已收录的历史条目一律保留。
每天随日期自动向后滑动，因此每次巡检只需维护**新进入窗口的那一天**。

> 窗口在 2026-09-15 由原来的「半个月」扩至 2 个月。当次已一次性回溯补齐

> 9/15 又因 LEVEL-5「LEVEL5 VISION 2026 II 夢」发布会新增 8 条，条目总数 50 → 58。
> 同日主机・PC 区拉齐到手游区精度（同款大卡 + 同 10 类维度）：**渲染层已全量对称**，
> `console` 数据块分批回填中，进度见文末「主机・PC 精度回填进度」。

## 卡片排序

卡片默认按**最新抓取**排序，规则是「抓取时间倒序 → 情报日期倒序」：

| 排序键 | 含义 | 字段 |
|---|---|---|
| ① 抓取时间 | 该条目**最后一次被巡检抓取 / 写入**的日期（观测台侧时间） | `capturedAt` |
| ② 情报日期 | 作品侧**最新情报事件日**（发表 / 定档 / 重要进展） | `announceDate` |

之所以分两级：同一场巡检会一次录入好几条，它们的 `capturedAt` 完全相同，
这时再用作品自身的 `announceDate` 定次序，才是读者能验证的「新」。
`capturedAt` 只在**新增或有情报更新**时才刷成本次运行日期——没动过的条目保持原值，
否则所有条目会挤在同一天，排序退化。

工具栏排序下拉共 5 项，**默认「最新抓取排序」**：

| 选项 | 规则 |
|---|---|
| 最新抓取排序（默认） | `capturedAt` ↓ → `announceDate` ↓ |
| 情报日期排序 | `announceDate` ↓ |
| 期待度排序 | `hype.score` ↓ |
| 公司排序 | `company`（日文五十音顺） |
| 发售 / 配信状态排序 | 两个作品区均可选：预约受理中 → 发售・配信日未定 → 已发售・已配信 |

> `announceDate` 允许只到月份（如 `2026-09`）。这类按**月初**参与比较，
> 因此会排在同月内标注了具体日期的条目之后——信息更精确的靠前。
> 另：`announceDate` **不放发售日**，发售日在 `release` 字段里；填未来日期会让条目错误地排到最前。

## 打开方式

双击 `index.html` 即可（纯静态，无需服务器、无外部依赖、可离线查看）。

## 目录结构

```
jp-game-observatory/
├── index.html          页面骨架（Tab / KPI / 工具栏 / 抽屉）
├── assets/
│   ├── style.css       暗色观测台主题
│   └── app.js          渲染与交互（筛选、排序、搜索、详情抽屉）
└── data/
    └── data.js         ★ 唯一数据源 — 自动巡检任务只改这个文件
```

`data/data.js` 用 `window.OBSERVATORY = {...}` 挂载，经 `<script src>` 引入，
因此 `file://` 直接打开也能加载，不受浏览器跨域限制。

## 页面模块

页面按**手游优先**编排：手游是重点信息区，主机 / PC 为次要区。

| 模块 | 内容 |
|---|---|
| KPI 行 | 手游条目 · 事前登录中 · 已配信 · 手游厂商 ／ 主机・PC 条目 · 厂商覆盖 |
| 本期综述 | 观测窗口内的整体判断（7 条要点，手游视角优先） |
| **手游新作（重点区）** | 每张卡含 10 类维度（见下）。配信状况 / 对应 OS / 课金形态 / 开发配信体制 / 配信地域 / 事前登录 / 玩法特征 / 世界观 / CV 阵容 / IP 系谱。跨平台作品额外标注「跨平台」徽章并列出全平台 |
| **主机・PC（次要区）** | 与手游区**同款大卡、同 10 类维度**。发售状况 / 对应机种 / 版本与价格 / 开发发行体制 / 发售区域 / 预约特典 / 玩法特征 / 世界观 / CV 阵容 / IP 系谱。支持平台筛选与卡片／紧凑两种视图 |
| **厂商覆盖** | 指定 50 家厂商监测名单，按四分类展示覆盖状态，可展开关联作品 |
| 期待榜 | Famitsu 读者期待榜（含票数条形对比） |
| TGS2026 前瞻 | 会期、主题、各社展位与展出内容 |
| 详情抽屉 | 点卡片展开：手游条目额外展示 Mobile Spec 区块；主机・PC 条目额外展示 Console Spec 区块（10 行规格 + 预约特典 + 玩法 / 世界观 / CV） |

两个作品区都支持按**发售 / 配信状态**排序（预约受理中 → 发售・配信日未定 → 已发售・已配信）、
按平台筛选、以及卡片／紧凑视图切换（紧凑视图收起特征区块、摘要收到 2 行）。

**跨平台作品两边都收**：`platformClass: "multi"`（手机 + 主机或手机 + PC）的作品，
既能在手机上玩、也是主机/PC 作品，因此**同时出现在手游区与主机・PC 区**，
手游区的卡片会打上「跨平台」徽章并额外列出全平台，避免只写 iOS/Android 造成误解。
（因此两侧条目数之和不等于总数，KPI 里有对应说明。）

交互：Tab 切换、全文搜索、平台筛选、五种排序（最新抓取 / 情报日期 / 期待度 / 公司 / 配信状态，默认最新抓取）、
卡片与紧凑两种视图、ESC 关闭抽屉。

## 数据字段

```js
{
  id, company, companyJp, bucket,          // bucket: "new" | "update"
  platformClass,                           // "mobile" | "pc" | "console" | "multi"（全部条目显式标注）
  announceDate,                            // 作品侧时间：最新情报事件日（发表 / 定档 / 重要进展），不放发售日
  capturedAt,                              // 观测台侧时间：该条目最后一次被抓取写入的日期（YYYY-MM-DD）
  title: { jp, cn, en },
  genre, platforms[], release, releasePrecision,
  summary,                                 // 内容摘要
  highlight,                               // 一句话要点
  news:   [{ source, url }],               // 新闻原文与参考来源
  videos: [{ label, platform, url }],      // 实机 / 预告 / 官方渠道
  hype:   { score, signals[] },            // 期待度 0-100 + 评估依据
  tags[], caution,                         // 可选

  /* 手游专属维度（platformClass: "mobile" 时必填，卡片与抽屉均据此渲染） */
  mobile: {
    status,        // 配信状况：事前登録受付中 / 配信予定 / 正式サービス中
    os[],          // 对应 OS
    monetization,  // 课金形态
    preReg: { open, since, reward },   // 事前登录（open=true 时卡片高亮展示）
    developer, publisher,
    region,        // 配信地域
    distribution,  // 配信方式（如「ブラウザ配信」）
    payment[],     // 支付手段
    ipSource, series,   // IP 出处 / 系列背景
    features[],    // 玩法特征
    synopsis,      // 世界观 / 故事
    cast           // 角色与配音
  },

  /* 主机・PC 侧维度（与 mobile 逐位对位，字段名一一对应；卡片与抽屉均据此渲染）。
     尚未回填的条目退化为用 release / platforms / company / genre 推导，
     推导不出的维度**直接不渲染** —— 不写「未発表」占位，
     免得把「我们还没查到」伪装成「官方尚未发表」。 */
  console: {
    status,        // 发售状况：発売中 / 発売予定 / 発売時期未発表  ←→ mobile.status（配信状况）
    os[],          // 对应机种（= 全平台列表）。可省略，省略时回落到 platforms
    monetization,  // 版本形态与价格（通常版 / 限定版 / DL 専売 ＋ 価格）  ←→ mobile.monetization
    developer, publisher,
    region,        // 发售区域       ←→ mobile.region
    distribution,  // 流通方式（パッケージ / ダウンロード）  ←→ mobile.distribution
    stores[],      // 对应商店（Nintendo eShop / PlayStation Store / Steam / Microsoft Store）
    preOrder: { open, since, reward },  // ←→ mobile.preReg，预约・早期购入特典
    features[], synopsis, cast,
    ipSource, series
  }
}
```

### 两区 10 类维度对位表

| # | 手游区 | 主机・PC 区 |
|---|---|---|
| 1 | 配信状況 | 発売状況 |
| 2 | 対応 OS | 対応機種 |
| 3 | 課金形態 | 販売形態 / 価格 |
| 4 | 開発 / 配信 | 開発 / 発売 |
| 5 | 配信地域 | 発売区域 |
| 6 | 事前登録 | 予約・早期購入特典 |
| 7 | 玩法特征 | 玩法特征 |
| 8 | 世界观 / 故事 | 世界观 / 故事 |
| 9 | 角色 / 配音 | CV 阵容 |
| 10 | IP / 系列背景 | IP / 系列背景 |

> 抽屉内主机条目另有 `流通方式` / `対応ストア` / `IP 出处` / `系列背景` 共 10 行规格，
> 与手游抽屉的 10 行（含 `配信方式` / `決済手段`）同样对位。**语言対応不设为一等维度**
> （与手游完全对位）；少数作品的中文语言情报写在 `caution` 里。

`platformClass` 现在**全部条目均显式标注**（`mobile` 13 / `multi` 5 / `pc` 3 / `console` 37，合计 58）。
若某条遗漏，`app.js` 的 `platformClassOf` 会从 `platforms` 兜底推断：
含 iOS / Android / 浏览器且不含主机平台 → `mobile`；两者都有 → `multi`。
新增条目请**显式写出**该字段，不要依赖推断。

另有 `meta`（更新时点、观测窗口、数据源清单、期待度口径说明）、
`companies`（厂商监测名单）、`mostWanted`（期待榜）、`tgs`（展会信息）、`digest`（本期综述）。

## 来源与链接策略（重要）

本台**只收录真实存在、可点开的来源**，不接受任何推测性链接。

**禁止两类别名链接：**

| 禁止 | 原因 |
|---|---|
| `youtube.com/results?search_query=...`、`x.com/search?q=...` 等**搜索结果页** | 不是具体内容页，链接会随检索结果漂移，对读者无意义 |
| **未经原文明确写出的**社媒账号（如 `@xxx_pr`）或频道 handle | 属于推测，极易指向不存在或错误的账号 |

**允许的来源类型**（不必强求 YouTube / X 两个平台）：

- 官方新闻稿 / 官方作品页 / 官方 X（原文中明确出现的账号）
- 日本游戏媒体：AppBank / GameBiz / QooApp / ファミ通 / 4Gamer / GameMeca / 電ファミ etc.
- 海外媒体：Anime News Network / Eurogamer / Polygon / Gurugamer / VICE etc.
- 商店页：Steam / App Store / Google Play（商店页自带预告影像，可作视频源）

**判定标准**：一条媒体把信息说清楚 + 一条来源能把影像放出来，即视为达标。
拿不到确切视频 ID 时，**退回到报道该作品的媒体文章页**（文中通常内嵌 PV），
而不是拼凑搜索页链接或猜测账号名。

> 环境限制：本机沙箱无法访问 `youtube.com` / `x.com` / `play.google.com` /
> `store.steampowered.com` 等域名，因此**无法自动做外链存活探测**。
> 链接真实性目前依赖"必须来自实际检索结果"这一条人工可核查的规则来保证。

## 期待度口径

```
期待度 = 日本侧信号（Famitsu / 媒体期待榜票数与排位）× 40%
       + 全球媒体覆盖广度（多语种媒体报道量）× 30%
       + 社媒与预告片声量 × 30%
```

**这是公开信号的定性综合评估，不是平台真实流量数据**，仅供趋势横向比较。
每个条目的 `hype.signals` 都列出了该分数的具体依据，页面详情抽屉内可查。

## 自动更新

已挂**每日两次**巡检任务（09:00 / 19:00，自 2026-09-16 起）：自动搜索日本游戏媒体 → 识别新增作品与状态变更 →
写回 `data/data.js` → 校验结构 → 推送到 GitHub Pages。

两场分工：**09:00 场**覆盖「前一日傍晚 ~ 当日早晨」的日媒消息；**19:00 场**覆盖「当日白天 ~ 晚间」的通稿。
每场都是基于当前 `data.js` 的增量更新，检索不到新内容时不会硬造条目。

巡检任务的硬约束：

- **只写 `data/data.js`**，不改 `index.html` / `assets/*`
- **绝不编造作品名、发售日、视频 ID、社媒账号**
- **不使用搜索页链接**，来源必须是实际检索命中的具体页面
- 每条至少 1 个 `news` 源、1 个 `videos` 源；手游条目必须带完整 `mobile` 子对象
- **主机・PC 条目逐步补齐 `console` 子对象**（与 `mobile` 逐位对位）：能核到官方口径的字段照填，
  核不到的**直接不写该字段**；只有官方明确表示「尚未公开」时才填 `未発表`
- **新增 / 更新的条目必须把 `capturedAt` 刷成本次运行日期**；未改动的条目保持原值（否则默认排序失去区分度）
- **`announceDate` 不得晚于今日**，也不得直接填发售日
